# 식단 기록 보강 — 사진 없는 기록·자주 먹는 음식·주의 영양소·기간 통계 (백엔드) 설계

작성일: 2026-07-29
모듈: `apps/daily-record`
바탕 문서: `docs/superpowers/specs/2026-07-27-diet-tracking-backend-design.md` (이 문서는 그 위에 얹는 증분이다)
짝 문서: `woori-haru/docs/superpowers/specs/2026-07-27-diet-tracking-ios-design.md`

## 배경

식단 도메인 1차 구현을 끝낸 뒤 필라이즈(같은 목적의 상용 앱)와 공개 자료 기준으로 기능을
대조했다. 점수 방식은 오히려 같은 방향이었다 — 필라이즈도 "적게 먹어도 균형 잡힌 비율이면
높은 점수"로 개편했고 절대 섭취량은 하루 단위에서만 본다. 우리 「끼니는 균형, 하루는 목표
대비 총량」과 같은 구조다.

갈린 것은 **기록을 계속하게 만드는 장치**였다. 네 가지가 빠져 있었고, 그중 둘은 우리 설계가
스스로 근거로 들었던 것을 구현하지 않은 자기모순이다.

## 범위

우선순위 순서다. **①과 ②가 「기록을 계속하게 만드는」 축이고, ③④는 기록이 쌓인 뒤에 값이
생긴다.** 이 순서로 만든다.

| # | 기능 | 왜 |
| --- | --- | --- |
| ① | 사진 없는 기록 | 지금은 사진 없이 끼니를 만들 수 없다. 과자 하나를 기록하려 사진을 찍게 만들면 기록률이 떨어진다 |
| ② | 자주 먹는 음식 | 설계가 `MealItem`을 쪼갠 첫 번째 근거인데 꺼내는 API가 없었다 |
| ③ | 주의 영양소 | 원본 데이터에 당류·나트륨·식이섬유가 있는데 정제 단계에서 버리고 있었다 |
| ④ | 기간 통계 | 1차에서 "주간 리포트"를 범위 외로 뺐던 것을 되돌린다 |

## 결정 사항

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 사진 없는 기록의 입력 | 식품DB 검색 + 직접 입력 | LLM 호출이 늘지 않는다. 텍스트 파싱은 나중에 필요해지면 얹는다 |
| 영양소 환산 주체 | 클라이언트 | 서버 변경이 작고 기존 확정 경로와 모양이 같다. **환산식이 두 곳에 사는 것은 감수한다** |
| 자주 먹는 음식의 원본 | `Food`가 아니라 과거 `MealItem` | 직접 입력 항목도 재사용되고, 담을 때 수량이 딸려온다 |
| 목록 정렬 | 빈도순, 동률이면 최근순 | 주식처럼 매일 먹는 것이 위로 온다 |
| 주의 영양소 반영 범위 | 저장·기준 대비 표시까지. **점수 공식은 건드리지 않는다** | 「범위를 벗어난 만큼만 감점」이라는 한 문장 설명을 지킨다 |
| 미매칭 항목의 주의 영양소 | 탄단지와 똑같이 LLM에게 받는다 | 0은 「없음」이 아니라 합계를 왜곡하는 값이고, **항상 안전한 쪽으로** 틀린다 |
| 기간 통계의 조언 | 넣지 않는다 (순수 집계) | LLM을 붙이면 하루 피드백에서 두 번 겪은 캐시 무효화 문제가 같은 모양으로 또 생긴다 |

## ① 사진 없는 기록

`MealConfirmRequest.analysisId`를 **nullable**로 바꾼다. null이면 `MealService.confirm`이
분석 조회·`attachFile`·분석 삭제를 통째로 건너뛰고, `MealPhoto` 없이 `Meal`을 만든다.
값이 있으면 지금 경로 그대로다.

```
POST /diet/meals {date, mealType, analysisId?, items}
```

`items`는 형태를 바꾸지 않는다. 클라이언트가 검색 결과나 직접 입력으로 조립해 지금과
똑같이 보낸다. 프로필은 여전히 필수다 — 목표 스냅샷을 떠야 하기 때문이다.

**서버 변경은 이게 전부다.** 삭제 시 `detachFiles`는 빈 목록에 이미 no-op이고, 조회의
`getPresignedUrls`도 마찬가지다. 응답의 `photos`가 빈 배열일 수 있다는 것만 앱 쪽 변화다.

**환산식이 앱에도 생긴다.** 검색해서 고른 음식은 100g당 값만 있으므로 앱이
`quantityG / 100 × per100g`을 계산해 보낸다. 서버의 `Food.nutritionFor`와 같은 식이어야 하며,
저장된 수치가 이상하면 여기를 먼저 의심한다. 이것을 감수하는 대신 서버 변경이 한 줄로 끝난다.

## ② 자주 먹는 음식

```
GET /diet/items/frequent?days=30&size=20
```

응답 한 건이 그대로 `MealItemRequest`가 되도록 필드를 맞춘다 — 앱이 탭 한 번으로 담는다.

```json
[{"foodName":"제육볶음","foodCode":"D101-...","quantityG":150.0,
  "kcal":300.0,"carbsG":15.0,"proteinG":30.0,"fatG":8.0,
  "sugarG":2.1,"sodiumMg":620,"fiberG":1.4,
  "source":"DB_MATCHED","count":7,"lastEatenOn":"2026-07-28"}]
```

> `sugarG`·`sodiumMg`·`fiberG`는 ③을 만든 뒤에 채워진다. ②를 먼저 만들 때는 이 세 필드가
> 응답에 없다.
>
> **2026-07-29 정정 — 원래 여기에 "③에서 컬럼이 생기면 자연히 따라 붙는다"고 적었는데, 안 붙었다.**
> ③은 `MealItem`에 컬럼을 더할 뿐이고 이 DTO를 고치는 것은 별개의 일이다. 태스크 경계로 나눠
> 리뷰하면 아무도 안 보는 자리라, 최종 리뷰에서야 잡혔다. **③을 만들 때 이 DTO를 함께 고쳐라.**

**같은 음식으로 묶는 키는 `foodCode`, 없으면 정규화한 이름**(`FoodNameNormalizer` 재사용)이다.
직접 입력한 이름의 띄어쓰기·대소문자 차이를 흡수한다. 표시 이름과 수량·영양소는 그 묶음에서
**가장 최근 항목**의 값을 쓴다 — 마지막에 먹은 양이 다음에 먹을 양에 가장 가깝다.

집계는 기간 내 `MealItem`을 `Meal`과 조인해 **한 번에 읽고 메모리에서 그룹핑**한다.
`group by`로 빈도를 구한 뒤 대표 항목을 다시 찾으면 N+1이 되는데, 사용자 2명·30일이면
많아야 수백 건이라 그 복잡도를 낼 이유가 없다.

`days`는 기본 30, 상한 90으로 클램프한다. `size`는 기본 20, 상한 50.

## ③ 주의 영양소

### 저장

원본(식약처 표준데이터)에 **두 데이터셋 모두** 당류(g)·식이섬유(g)·나트륨(mg)이 있다.
정제 스크립트에서 세 컬럼을 더 남긴다. 이름은 여전히 **마지막 컬럼**이어야 하므로 순서는:

```
code,servingSizeG,kcalPer100g,carbsPer100g,proteinPer100g,fatPer100g,sugarPer100g,sodiumMgPer100g,fiberPer100g,name
```

필드가 늘어나는 곳 — `Food`(100g당 3개), `MealItem`(3개), `Meal`(합계 3개),
`NutritionProfile`(목표 3개), `Meal` 확정 스냅샷(목표 3개), 그리고 **값이 흘러가는 DTO 둘**:

- `AnalyzedItem`(인식 결과) — 이게 없으면 `MealAnalyzer`가 `Food.nutritionFor`로 계산한 값을
  버리고, **사진으로 기록한 모든 끼니가 나트륨 0으로 저장된다.**
- `FrequentItemResponse`(자주 먹는 음식) — 이게 없으면 탭 한 번으로 담은 항목도 0이 된다.

> **2026-07-29 개정 — 이 목록에서 DTO 둘이 빠져 있었고, 실제로 그대로 구현돼 최종 리뷰에서
> Critical로 잡혔다.** 결과가 단순한 결측이 아니라 **거짓 판정**이었다 — 나트륨 0이면 라면을
> 먹어도 매일 「기준 이하」, 식이섬유 0이면 매일 「기준 미달」이 뜬다. 값이 저장되는 자리만
> 세고 **흘러가는 자리**를 안 센 것이 원인이다. 다음에 영양소를 더할 때 같은 실수를 하지 않으려면
> 경로 전체를 따라가야 한다: 식품DB(100g당) → `Food.nutritionFor` → `AnalyzedItem`(인식) 또는
> `FrequentItemResponse`(재사용) → `MealItemRequest` → `MealItem` → `Meal` 합계 → 하루 판정.

### 미매칭 항목도 세 값을 LLM에게 받는다

> **2026-07-29 개정 — 원래 이 자리에 「LLM 추정 항목은 세 값이 0이다」라고 적혀 있었다. 뒤집는다.**

식품DB에 매칭되지 않은 음식은 **이미 열량·탄수·단백·지방을 LLM 추정값으로 받아 쓰고 있다**
(`RecognizedFood.estimated*`). 거기에 당류·나트륨·식이섬유만 묻지 않을 근거가 없다. 근거로
적었던 「LLM에게 영양소 수치를 묻지 않는다」는 원래 매칭에 **성공한** 항목에 대한 이야기였다 —
같은 사진에서 호출마다 값이 흔들리는 것을 막으려는 규칙이지, 매칭이 실패해 어차피 추정에
기대는 자리에까지 적용할 규칙이 아니었다.

0을 두는 쪽이 더 위험하다. **0은 「데이터 없음」이 아니라 합계에 더해지는 틀린 숫자이고, 항상
안전한 쪽으로 틀린다** — 나트륨을 과소평가하고 식이섬유를 과소평가한다. 이 절이 존재하는 이유가
나트륨 경고인데 그것만 안 뜨게 된다.

판정이 임계값 비교라는 점도 같은 방향을 가리킨다. 절대값보다 순서가 중요하다:

| | 실제 3,500mg인 날의 합계 | 판정 |
| --- | --- | --- |
| 0으로 두면 | 약 1,200mg | 안전 ← 뒤집힘 |
| LLM 추정 | 약 2,800mg | 초과 ← 맞음 |

40% 틀려도 판정은 맞는다. 그리고 「라면은 짜다」는 사진에서 양을 가늠하는 것(탄단지 오차의
주원인)보다 LLM에게 오히려 쉬운 종류의 판단이다.

`RecognizedFood`에 `estimatedSugarG`·`estimatedSodiumMg`·`estimatedFiberG`를 더하고, 프롬프트와
`json_schema`의 `properties`·`required`에도 넣는다(`strict: true`라 `required`가 빠지면 호출이
거부된다). `MealAnalyzer`의 미매칭 분기가 그대로 `AnalyzedItem`에 옮긴다. **호출 횟수는 그대로**고
토큰 증가는 무시할 수준이다.

### 추정이 섞였다는 것은 표시한다

추정값을 넣어도 판정이 틀릴 수 있다는 사실은 사라지지 않는다 — 틀리는 이유가 0에서 오차로
바뀔 뿐이다. 그래서 `GET /diet/days/{date}` 응답에 그날 추정 항목이 몇 건인지 싣는다.

```json
"estimatedItemCount": 2
```

항목 단위로는 `NutritionSource.LLM_ESTIMATED` 배지가 이미 있지만 하루 판정까지 흘러가지 않는다.
세 영양소가 모두 같은 항목 집합에서 오므로 `NutrientLimit`마다 반복하지 않고 **하루 단위로 한 번만**
내려준다. 앱은 `nutrientLimits` 옆에 「추정 N건 포함」을 붙인다.

**기간 통계(④)에는 넣지 않는다.** 거기에는 `OK`/`WARN` 판정이 없고 평균만 있어서, 사용자가
「안전하다」고 믿게 되는 자리가 아니다.

**이것으로도 안 잡히는 결측이 남는다.** 가공식품 데이터셋은 식이섬유가 2.9% 비어 있는데 정제
스크립트가 빈 값을 0으로 채우므로, `DB_MATCHED` 항목에도 조용한 0이 섞인다. 구분하려면 `Food`의
세 컬럼을 nullable로 바꾸고 합계·판정까지 전부 null을 다뤄야 해서 이번에는 하지 않는다.

**CSV 포맷이 바뀌므로 `food` 테이블을 비우고 다시 적재해야 한다.** 시더는 테이블이 비어
있을 때만 돌기 때문이다. 배포 절차에 `truncate food` 한 줄이 필요하다.

**배포 전에 `meal`·`meal_item`·`nutrition_profile`이 비어 있는지도 확인해야 한다.** 이 셋에도
`nullable = false` 컬럼이 3개씩 늘어나는데, **`ddl-auto: update`는 행이 있는 테이블에 NOT NULL
컬럼을 붙이지 못한다** — PostgreSQL이 거부하고 Hibernate는 경고만 남기고 넘어가서, **컬럼이
없는 채로 앱이 뜬다.** 식단 테이블은 아직 배포된 적이 없어 지금은 문제가 아니지만, 다음에
컬럼을 더할 때는 이 확인이 절차에 있어야 한다.

**기존 `nutrition_profile` 행은 목표 3개가 0이다.** 프로필을 저장하거나 몸무게를 갱신해야
채워진다. 그 전에 확정한 끼니는 「0mg 이하」 같은 스냅샷을 영구히 갖게 되므로, 배포 후
사용자에게 프로필을 한 번 저장하게 안내해야 한다.

이 도메인은 새 테이블을 만들지 않는다 — ③은 컬럼만 늘리고 ①②④는 스키마를 건드리지 않는다.
(테이블명 관례는 2026-07-29부터 단수형이다. `ddl-auto: update`가 rename을 못 해서 식단
도메인만 바꿨고, 배포된 적 없는 테이블이라 가능했다.)

### 기준값 — 전부 KDRIs에서 온다

| 영양소 | 기준 | 성격 |
| --- | --- | --- |
| 나트륨 | 2,300mg 이하 | 만성질환위험감소섭취량(성인) |
| 식이섬유 | 남 30g / 여 20g 이상 | 충분섭취량(19~64세) |
| 총당류 | 목표 칼로리의 20% 이하 | 에너지적정비율 상한(총당류 10~20%) |

당류는 **총당류** 기준이다. 첨가당(10% 미만)과 다르며, 식품DB의 당류 컬럼도 총당류라 맞물린다.
식이섬유가 성별에, 당류가 목표 칼로리에 걸리므로 **이 셋도 `Meal` 스냅샷에 넣는다** — 넣지
않으면 성별·몸무게가 바뀔 때 과거 하루 기록의 판정이 소급 변경된다. 프로필이 목표 4개를
계산할 때 함께 구해 저장하고, 확정 시 복사한다.

### 응답

`GET /diet/days/{date}`에 `nutrientLimits` 절을 더한다. **점수에 들어가지 않으므로 `penalty`가
없다.** 판정은 서버가 한다 — `scoreBasis`와 같은 원칙이다(앱이 판정하면 규칙이 두 곳에 생긴다).

```json
"nutrientLimits": [
  {"name":"나트륨","intake":2850,"unit":"mg","standardText":"2,300mg 이하","status":"WARN"},
  {"name":"식이섬유","intake":12.4,"unit":"g","standardText":"30g 이상","status":"WARN"},
  {"name":"당류","intake":48.0,"unit":"g","standardText":"125g 이하","status":"OK"}
],
"estimatedItemCount": 2
```

`estimatedItemCount`는 기록이 없는 날에도 `0`으로 내려간다 — 앱이 null 분기를 만들지 않도록.

`status`는 `OK`/`WARN` 둘뿐이다. 항목마다 문제가 되는 방향이 다른데(나트륨은 초과, 식이섬유는
미달) 앱이 그 방향을 알 필요는 없다. `standardText`가 사람이 읽는 문구를 그대로 담으므로
기준이 개정돼도 앱 배포 없이 문구가 따라간다.

### 피드백

**하루 프롬프트에만 넣는다.** 나트륨 기준 자체가 하루 단위이고, 끼니 프롬프트는 2026-07-29
개정에서 하루 맥락을 걷어내 균형만 보도록 정리했다. 거기에 나트륨을 다시 넣으면 그 정리를
되돌리는 셈이 된다.

## ④ 기간 통계

```
GET /diet/stats?from=&to=
```

주·월을 한 엔드포인트로 처리한다. `GET /diet/meals?from=&to=`가 이미 같은 모양이다.

기간 내 `Meal`을 한 번 읽어 날짜별로 묶고, **각 날의 첫 끼니 스냅샷 목표**로 그날 점수를
계산한다(하루 집계와 같은 규칙이라 값이 어긋나지 않는다).

```json
{"from":"2026-07-22","to":"2026-07-28","recordedDays":6,
 "averageDayScore":74,
 "dailyScores":[{"date":"2026-07-22","dayScore":81}, ...],
 "averageIntake":{"kcal":1980.0,"carbsG":250.1,"proteinG":78.4,"fatG":62.0,
                  "sugarG":44.2,"sodiumMg":2610,"fiberG":14.8},
 "averageTargets":{"kcal":2509,"carbsG":345,"proteinG":94,"fatG":84},
 "topFoods":[...]}
```

`recordedDays`는 기록이 하나라도 있는 날의 수다. **평균은 기록한 날로만 나눈다** — 안 먹은
게 아니라 안 적은 날을 0으로 세면 평균이 무의미해진다.

`averageTargets`는 기간 내 각 날 첫 끼니 스냅샷 목표의 평균이다. 몸무게가 바뀌면 목표도
바뀌므로 기간 평균이 하나로 고정되지 않는다.

`topFoods`는 ②의 집계를 같은 기간으로 돌린 결과다. 코드를 공유한다.

기간이 366일을 넘거나 `from > to`면 `INVALID_REQUEST`다(클램프가 아니라 거절이다 — 조용히
줄이면 사용자가 요청한 것과 다른 기간의 숫자를 보게 된다). 구현은 `from.plusDays(366) < to`라
양끝 포함 367일까지 허용한다 — 1년치를 요청할 때 걸리지 않게 하려는 여유다.

**캐시도 무효화도 없다.** 전부 `Meal` 합산이라 언제 계산해도 같은 값이 나온다.

## 실패 처리

| 상황 | 처리 |
| --- | --- |
| 사진 없는 확정에서 `items`가 빔 | `INVALID_REQUEST` (기존 검증 그대로) |
| 프로필 없이 확정 | `PROFILE_NOT_FOUND` (기존 그대로) — 사진 유무와 무관하다 |
| 자주 먹는 음식이 없음(신규 사용자) | 빈 배열. 오류가 아니다 |
| 식품DB에 당류·나트륨이 결측인 행 | 0으로 적재한다. 버리면 그 음식 자체를 못 쓰게 되는데, 탄단지는 멀쩡하므로 손실이 크다 |
| 기간 통계에 `Meal`이 0건 | `recordedDays: 0`, `averageDayScore: null`, 나머지 배열은 빈 값 |

## 테스트

- `MealConfirmTest` — `analysisId`가 null이면 `attachFile`·분석 삭제를 부르지 않고 `photos`가 비는지, 있으면 기존 경로가 그대로인지
- `FrequentItemServiceTest` — 빈도순 정렬, 동률 시 최근순, `foodCode` 없는 항목이 정규화 이름으로 묶이는지, 대표 값이 가장 최근 항목인지, `days` 클램프
- `NutritionTargetCalculatorTest` — 나트륨·식이섬유·당류 목표가 성별·목표 칼로리에서 나오는지
- `DailyDietServiceTest` — `nutrientLimits`의 `status` 판정(경계값 포함), 스냅샷 기준을 쓰는지(프로필을 바꿔도 과거 판정이 그대로인지)
- `DietStatsServiceTest` — 기록한 날로만 평균을 내는지, 날짜별 점수가 그날 첫 끼니 스냅샷으로 계산되는지, 0건일 때 null
- `FoodCsvParserTest` — 늘어난 컬럼 순서, 당류·나트륨 결측이 0으로 채워지는지

## 범위 외

텍스트로 적으면 LLM이 정리하는 입력 · 식단 추천 · 체중 추이 그래프 · 물 섭취 ·
주의 영양소의 점수 반영 · 기간 조언(LLM) · 배우자 공유.

**텍스트 입력은 가장 가까운 후보다.** `OpenRouterClient.generateText`에 `json_schema`만 붙이면
되고, 그 뒤는 사진 경로와 똑같이 식품DB 매칭·확인 화면을 탄다. ①을 써 보고 검색이 번거롭다는
게 확인되면 그때 얹는다.
