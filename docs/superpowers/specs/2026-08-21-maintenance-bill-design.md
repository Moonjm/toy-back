# 관리비 고지서 사진 인식·기록 설계

작성일: 2026-08-21
모듈: `apps/daily-record` — `com.toy.backend.maintenance`

## 배경

매달 종이로 오는 **아파트 관리비 납입영수증(입주자용)**을 사진으로 찍어 올리면 항목별
금액과 사용량이 기록되고, 달마다 어떻게 변해 왔는지 추이를 보려는 것이다.

**가계부(ledger)와는 연동하지 않는다.** 관리비는 카드 자동납부로 나가고 있어
`AutoPaymentParser`가 이미 가계부에 지출 1건을 쌓는다. 확정 시 `LedgerEntry`를 또 만들면
같은 돈이 두 번 잡혀 월 지출이 부풀려진다. 관리비 화면의 목적은 **항목별 추이**이지
지출 합계를 다시 내는 것이 아니다.

### 두 가지 출처

과거 1년치가 두 형식으로 남아 있다.

- **2025-08 ~ 2025-11** — 관리비 앱(아파트아이) 화면 캡처. 세로 목록이고 항목·금액만 있다.
  연도·동·호·면적·납기일·사용량이 **아예 없다.**
- **2025-12 ~** — 종이 영수증 사진. 2단 표이고 사용량·납기일·동·호·면적이 함께 찍혀 있다.

**인식 기능은 종이 영수증만 대상으로 한다.** 앞의 네 달은 사람이 판독한 값을 SQL로 한 번
넣고 끝낸다 — 되풀이될 형식이 아닌데 그것까지 프롬프트가 감당하게 만들면, 두 형식 중 어느
쪽으로도 확실하지 않은 프롬프트가 된다.

### 항목 이름은 종이가 기준이다

같은 비용을 두 형식이 다르게 부른다.

| 앱 캡처 | 종이 영수증 |
|---|---|
| 세대전기료 | 전기 |
| 세대급탕비 | 온수 |
| 세대수도료 | 수도 |
| 세대난방비 | 난방 |

**종이 이름으로 통일하고, 앱 캡처 네 달치는 SQL을 넣을 때 그 이름으로 맞춰 넣는다.**
그러면 코드에 정규화 계층이 필요 없다. 반대로 두 이름을 그대로 두면 전기료 추이 그래프가
2025-11과 2025-12 사이에서 한 번 끊긴다.

## 실측 — 근거 데이터

설계 전에 실제 사진으로 OpenRouter를 호출해 측정했다. 아래 숫자가 이 설계의 근거다.
정답은 원본을 확대해 사람이 판독한 값이고, **네 장 모두 항목 합계가 영수증의 당월부과액과
일치하는 것으로 정답 자체를 검증했다.**

### 1차 — 정답 3장, 각 3회

| 모델 | 완전일치 | 비용/장 | 속도 |
|---|---|---|---|
| `gemini-2.5-flash` | 8/9 | $0.0029 | 6.4s |
| **`gemini-3.7-flash`** | **9/9** | **$0.0045** | 12.4s |

### 2차 — 종이 영수증 8장(2025-12 ~ 2026-07), 각 2회, `3.7-flash`

16회 전부 **합계 검증 통과**, 8장 전부 **실행 간 완전일치**, 정답 대조 가능한 3장 전부
**정답 일치**. 총 $0.0648.

`3.7-flash`는 `3.6-flash`(배차표용)의 정확히 절반 가격이다 — 입력 $0.375/M, 출력 $1.875/M.

## ⚠️ 먼저 읽을 함정 넷

### 함정 1 — **합계 검증은 사용량 오독을 못 잡는다**

`2.5-flash`가 유일하게 틀린 실행에서 **수도 사용량 10.8을 10.6으로** 읽었다.
그런데 **그 실행도 합계 검증은 통과했다.** 금액은 전부 맞았기 때문이다.

「Σ항목 == 당월부과액」은 금액 오독에만 걸리는 그물이고, 사용량은 그 그물 바깥에 있다.
사용량은 사람이 검수 화면에서 눈으로 봐야 하며, **자동 검증이 통과했다는 것을 사용량까지
맞다는 뜻으로 읽으면 안 된다.** 이 사실을 코드 주석에도 남긴다.

### 함정 2 — **`max_tokens`에 reasoning 토큰이 함께 잡힌다**

`3.7-flash`의 completion 토큰이 실측 1,773~2,333이다. 식단용 기본값(4,000)으로 두면
`content`가 빈 채로 온다. **30,000으로 둔다** — `dispatch`가 같은 이유로 같은 값을 쓴다.

`max_tokens`를 아예 안 보내는 것은 더 나쁘다. OpenRouter가 모델 최대 출력만큼 잔액을
선점해 잔액이 남았는데도 402가 난다.

### 함정 3 — **`관리비차감`은 음수다**

2026-03·2026-07에 `관리비차감 -13,790`이 있다. 금액 컬럼에 음수 제약을 걸면 그 달의
저장이 통째로 실패한다. 프롬프트에도 「`-`가 붙은 값은 음수 그대로」를 명시한다.

### 함정 4 — **strict 스키마는 정수라는 것만 보장한다**

`month`가 `13`으로 와도 스키마는 통과한다. 그대로 `YearMonth.of`에 넣으면
`DateTimeException`이 500으로 떨어져 서버 결함처럼 보인다. **범위를 손으로 확인한다**
(`dispatch`가 같은 함정을 이미 밟았다).

## 데이터 모델

### `maintenance_bills` — 월 1건

| 컬럼 | 비고 |
|---|---|
| `year_month` | **unique.** 한 달에 한 장이다 |
| `dong`, `ho`, `area_m2` | 영수증에 찍힌 값 |
| `charged_amount` | 당월부과액 |
| `discount_total`, `unpaid_amount`, `unpaid_late_fee` | 빈 칸이면 0 |
| `due_amount`, `due_date` | 납기내 금액·날짜. 앱 캡처 출처는 `due_date`가 null |
| `electricity_kwh`, `water_m3`, `hot_water_m3`, `heating_gcal`, `food_kg` | 없는 달은 null |

**동·호·면적을 매 건 저장한다.** 한 집 고정값이라 중복이지만, **옆집 영수증을 잘못 올렸는지
잡는 유일한 단서**다. 설정값과 다르면 검수 화면이 경고한다.

**사용량은 컬럼으로 둔다.** 5종 고정이고 목적이 추이 그래프다. 별도 테이블로 빼면 추이
쿼리마다 피벗해야 한다. 여름에는 난방이 없으므로 null을 허용한다.

### `maintenance_bill_items` — 항목

`bill_id`, `name`, `amount`, `display_order`.

**항목은 테이블로 뺀다.** 달마다 21~22개로 개수가 바뀌고 새 이름이 생긴다
(`관리비차감`, `선거관리운영비`). 사용량과 반대 판단이며, 이유도 반대다.

금액은 저장소 관례대로 `BigDecimal(precision = 19, scale = 4)`이고 **음수를 허용한다.**

## API

```
POST   /maintenance/recognitions        사진 → 인식 결과만. 아무것도 저장하지 않는다
POST   /maintenance/bills               검수 확정분 저장. 같은 달이 있으면 409
GET    /maintenance/bills/{yearMonth}   한 달 상세
GET    /maintenance/bills               최근 목록
PUT    /maintenance/bills/{yearMonth}   덮어쓰기
DELETE /maintenance/bills/{yearMonth}
GET    /maintenance/trends              항목·사용량 월별 추이 + 전년 동월 비교
```

`GET /maintenance/trends`는 `months`(기본 13)를 받아 **최근 N개월**을 낸다. 13이 기본인
이유는 전년 동월이 범위 안에 들어와야 비교가 성립하기 때문이다. 응답은 월 목록 하나에
항목별 금액과 사용량을 함께 실어 내려, 화면이 그래프마다 따로 부르지 않게 한다.
**기간을 자유롭게 받지 않는다** — `dispatch`가 같은 이유로 연월 하나만 받는다.

**인식과 저장을 분리한다.** 인식 결과를 바로 저장하면 틀린 값이 조용히 박히고, 관리비는
틀렸다는 사실을 알려주지 않는다. `dispatch`가 같은 구조를 쓴다.

**같은 달 재업로드는 409로 막고 수정은 `PUT`으로 받는다.** 조용한 덮어쓰기는 검수를 마친
값을 인식 직후 값으로 되돌린다.

**사진은 저장하지 않는다.** `common/file`의 `FileEntity`에 소유자가 없는 미해결 이슈를
건드리지 않는다(AGENTS.md 참조).

**무인증으로 열지 않는다.** `dispatch`의 조회가 공개된 근거는 응답에 실명·차량번호가 없다는
것인데, 관리비 응답에는 동·호가 들어간다. 사용자에 묶지는 않는다 — 집이 하나고 부부가 함께
보는 데이터다.

### 검수 화면에 넘길 검증 플래그

- `sumMatched` — Σ항목 == 당월부과액. 실측 16/16 통과라 실패는 드물지만, 실패하면 금액
  오독이 거의 확실하다
- `addressMatched` — 설정된 동·호와 일치하는지
- 연·월 범위 검사 결과

**사용량에는 대응하는 플래그가 없다**(함정 1). 없는 것을 있는 척 만들지 않는다.

## 설정

`maintenance.*`로 분리한다. 식단이 `2.5-flash`, 배차가 `3.6-flash`, 관리비가 `3.7-flash`로
셋 다 다르다.

```yaml
maintenance:
  api-key: ${OPENROUTER_API_KEY:}
  base-url: https://openrouter.ai/api/v1
  vision-model: ${MAINTENANCE_VISION_MODEL:google/gemini-3.7-flash}
  vision-max-tokens: ${MAINTENANCE_VISION_MAX_TOKENS:30000}
  timeout-seconds: 120
  dong: ${MAINTENANCE_DONG:}
  ho: ${MAINTENANCE_HO:}
```

`dong`·`ho`는 `addressMatched` 판정에만 쓴다.

재시도는 `dispatch`와 같다 — 파싱 실패는 1회 재시도, `finish_reason == "length"`나 빈
content는 결정론적이라 재시도하지 않고, 4xx도 바로 포기한다.

동·호·면적은 같은 집이므로 영수증 값을 그대로 채운다.

## 테스트

- `MaintenanceVisionClient` — 프롬프트·스키마 구성, 파싱, 재시도 분기(kotest + mockk)
- 합계 검증·주소 대조·연월 범위 검사의 경계값
- 음수 항목(`관리비차감`)이 저장·조회를 통과하는지
- 추이 API — 항목이 있다가 없어지는 달(여름 난방)에서 그래프가 끊기지 않는지

단위 테스트는 리포지토리를 목으로 대체하므로 트랜잭션 경계와 DB 제약을 잡지 못한다.
`year_month` unique 제약과 409 분기는 **실제로 앱을 띄워 확인한다.**
