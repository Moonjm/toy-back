# 영양소 필드별 출처와 버려진 13,405행 되살리기 (백엔드) 설계

작성일: 2026-08-02
짝 저장소: `woori-haru` — 앱은 배지 하나만 붙이면 된다(맨 아래 「iOS가 할 일」).

## 배경

`Food`의 탄단지가 non-null `Double`이라 **「모른다」를 담을 자리가 없다.** 그래서 같은 결함이
두 얼굴로 나타난다.

**하나 — 아는 값까지 버린다.** `FoodCsvParser`가 탄수화물이나 지방이 비면 행을 통째로 버린다.

```kotlin
val kcal = columns[2].trim().toDoubleOrNull() ?: return null
val carbs = columns[3].trim().toDoubleOrNull() ?: return null   // ← 여기서 13,405행이 죽는다
```

음식DB 원본 19,495행 중 **13,405행(69%)이 이렇게 죽는다.** 그런데 그 13,405행은
**전부 열량과 단백질을 갖고 있다**(100%). 당류는 99%, 포화지방은 96%가 있다.
죽는 것들이 하필 자주 먹는 것들이다 — 피자 4,227 · 커피 1,647 · 스무디 1,011 · 라떼 904 ·
케이크 580 · 아이스크림 348 · 도넛 234 · 버거 223. 브랜드로 보면 파파존스 528 ·
뚜레쥬르 494 · 피자헛 373 · 스타벅스 213 · 교촌 49다.

**둘 — 추정값이 공식값인 척한다.** 2026-08-02에 넣은 수동 등록분 86행이 그렇다.
`한우불고기버거` 한 행 안에서 열량 217.5·단백질 8.75·나트륨 304.2는 롯데리아 공식값이고
탄수화물 18.42·지방 12.09는 우리가 계산한 값인데, 표도 화면도 그 둘을 구분하지 못한다.

프랜차이즈 영양성분표가 **어린이 기호식품 의무표시 항목(열량·단백질·나트륨·당류·포화지방)만**
싣기 때문에 브랜드 메뉴를 늘릴수록 이 비중이 커진다. BHC·네네·처갓집을 더 넣으려면 먼저 풀어야 한다.

## 결정

| 물음 | 결정 |
| --- | --- |
| 모르는 탄·지를 어떻게 담나 | **추정해서 채우고 「추정」 표시만 한다.** `Double`을 nullable로 바꾸지 않는다 |
| 출처를 어느 필드까지 | **탄·단·지 셋만.** 점수 계산에 쓰이는 값들이다 |
| 13,405행 되살리기 | **이번에 같이 한다** |

**nullable로 안 가는 이유** — `nutritionFor`·`MealItem` 스냅샷·끼니/하루 점수·`FoodResponse`·
iOS 디코딩까지 전부 null을 다뤄야 하는데, 얻는 것은 「점수를 낼 수 없어요」 화면이다.
피자·커피·라떼가 죽어 있던 목록이라 그 화면이 자주 뜬다. 추정의 실측 오차(아래)가
**안 넣었을 때보다 나쁘지 않다**는 것이 이미 확인돼 있어, 정확도를 위해 치를 값이 아니다.

**나머지 6개 영양소(당류·나트륨·식이섬유·포화·트랜스·콜레스테롤)에 출처를 안 다는 이유** —
표시 전용이라 점수에 영향이 없고, 지금 결측을 0으로 채우는 행이 30만 개라 화면이 배지투성이가 된다.

## 실측 — 추정이 얼마나 맞나

음식DB에서 탄·지를 아는 행을 하나씩 빼고 나머지로 맞혀 보는 홀드아웃으로 쟀다.

| | 탄 오차(중앙) | 지 오차(중앙) | 끼니 점수 오차 | **안 넣었을 때(부분 매칭)** |
| --- | --- | --- | --- | --- |
| 버거 72건 | 2.4g | 1.1g | 중앙 7.3 / p90 22.6 | 중앙 **7.7** |
| 닭튀김 23건 | 2.9g | 1.1g | 중앙 10.1 / p90 30.7 | 중앙 **12.7** |

그램 오차는 작은데 점수 오차가 큰 이유 — 점수가 50/65·15/30 경계에서 급변해서 몇 g 차이가
경계를 넘으면 감점이 확 바뀐다. **다만 안 넣었을 때와 같거나 낫다.** 실제로 좋아지는 것은
총량이다(1회 열량 오차 중앙 86kcal·최대 376kcal → 0, 나트륨 194mg → 0).

교차검증 하나 — 필라이즈가 `리아 두툼새우` 지방을 30g으로 싣는데 우리 추정이 31.6g이다(5% 차이).

## 스키마

```kotlin
class Food(
    // ... 기존 그대로. 탄단지는 non-null Double을 유지한다 ...

    /**
     * 추정으로 채운 필드. null이면 전부 원본 값이다. `"carbs,fat"`처럼 쉼표로 잇는다.
     *
     * **왜 필요한가** — 프랜차이즈 영양성분표는 어린이 기호식품 의무표시 항목만 싣는다.
     * 열량·단백질·나트륨은 공식값인데 탄수화물·지방은 우리가 잔여 열량에서 계산한 값이라,
     * 이 컬럼이 없으면 한 행 안에서 둘을 구분할 방법이 없다.
     *
     * 값은 `carbs` / `protein` / `fat` 셋뿐이다(`FoodPolicy.ESTIMABLE_FIELDS`).
     * 표시 전용 영양소는 담지 않는다 — 점수에 영향이 없고 결측이 30만 행이라 의미가 없다.
     *
     * `columnDefinition` 없이 nullable이라 `ddl-auto: update`가 기존 행에 그냥 붙인다.
     */
    @Column(name = "estimated_fields", length = 40)
    var estimatedFields: String? = null,
)
```

**컬럼 하나로 두는 이유** — `carbsEstimated`/`fatEstimated` 불리언 셋으로 두면 앞으로 필드가
늘 때마다 컬럼이 붙는다. 조회는 `estimated_fields is not null`(추정 섞인 행)과
`like '%carbs%'`(특정 필드)로 충분하고 둘 다 뜨거운 경로가 아니다.

`MealItem`에는 **넣지 않는다.** 확정 시점 스냅샷이라 나중에 출처를 되짚을 일이 없고,
`MealItem.source`(`DB_MATCHED`/`LLM_ESTIMATED`)가 이미 항목 단위 출처를 담고 있다.

## CSV 형식

`FoodCsvParser`의 컬럼을 **15개로 늘린다**(지금 14개). `name` 바로 앞에 넣는다 —
이름에 쉼표가 들어갈 수 있어 `name`은 반드시 마지막이어야 한다.

```
code,servingSizeG,kcalPer100g,carbsPer100g,proteinPer100g,fatPer100g,
sugarPer100g,sodiumMgPer100g,fiberPer100g,saturatedFatPer100g,
transFatPer100g,cholesterolMgPer100g,estimatedFields,maker,name
                                      ^^^^^^^^^^^^^^^ 새 컬럼
```

빈 칸이면 null이다. `"carbs,fat"`처럼 쉼표가 들어가므로 **CSV에서는 파이프로 쓴다**(`carbs|fat`) —
쉼표 구분 파일에 쉼표를 담을 수 없다. 파서가 파이프를 쉼표로 바꿔 저장한다.

## 추정 규칙

`scripts/build-lotteria-csv.py`가 쓰는 것과 **같은 규칙**이다. 그 스크립트에서 떼어내
`scripts/nutrition_estimate.py`로 옮기고 양쪽이 import 한다 — 규칙이 갈라지면 같은 음식이
경로에 따라 다른 값을 갖는다.

### 1. 잔여 열량을 분류별 탄:지 비중으로 나눈다

```
잔여 = 열량 − 4 × 단백질
탄수화물 = 잔여 × 비중 / 4
지방     = (잔여 − 4 × 탄수화물) / 9
```

비중은 **음식DB 분류 접두사**(`피자_`, `커피_`)별로, 탄단지가 완비되고 아트워터가 ±15% 안에
맞는 행들의 `4×탄 / (4×탄 + 9×지)` 중앙값이다.

| 분류 | 되살릴 행 | 기준 표본 | 비중 |
| --- | --- | --- | --- |
| 피자 | 4,227 | 459 | 0.511 |
| 커피 | 1,647 | 160 | 0.608 |
| 스무디 | 1,011 | 84 | 0.787 |
| 라떼 | 904 | 82 | 0.668 |
| 케이크 | 580 | 75 | 0.382 |
| 아이스크림 | 348 | 117 | 0.645 |
| 에이드 | 241 | 16 | 0.988 |
| 버거 | 223 | 72 | 0.404 |

**접두사로 잡는다. 부분 문자열로 잡으면 안 된다** — 롯데리아 작업 때 「콜라」가
`머핀_게랑트쇼콜라`를, 「소스」가 `삼각김밥_참치마요네즈`를 끌어와 비중이 통째로 오염됐다.
숫자는 멀쩡해 보이고 아무 데서도 안 걸린다.

### 2. 물리 하한 둘을 건다

- **당류 ≤ 탄수화물** — 당류는 탄수화물의 일부다
- **포화지방 ≤ 총지방**

없으면 사이다에 없는 지방이 생긴다. 탄산·에이드·아이스티는 당류가 잔여 열량의 91~98%라
사실상 이 하한이 값을 정한다(추정이 거의 개입하지 않는다). 되살릴 행의 99%가 당류를,
96%가 포화지방을 갖고 있어 대부분에 걸린다.

**열량은 공식값을 그대로 지킨다.** 두 하한이 동시에 잔여 열량을 넘으면 원본끼리 모순인
것이라, 그때는 하한 둘을 지키고 열량을 포기한다(경고를 남긴다).

### 3. 기준 표본이 5건 미만인 분류

표본 5건 기준으로 **13,405행 중 12,349행(92.1%)이 커버된다.** 남는 1,056행(7.9%)은:

- **차류 303행(29%)은 열량이 1kcal이다**(허브차 141 · 홍차 70 · 녹차 27). 잔여 열량이
  0에 가까워 무엇으로 나누든 값이 0이다. 그대로 되살린다
- **빵·디저트류는 별칭을 둔다** — 와플 196 → `도넛_`, 허니브레드 47 · 카스텔라 23 ·
  기타빵 34 · 타르트 19 → `케이크_`, 소세지빵 20 → `크림빵_`
- **그래도 기준이 없으면 지금처럼 버린다.** 근거 없는 전체 평균을 밀어 넣지 않는다.
  몇 건이 버려졌는지 스크립트가 표준에러로 남긴다

### 4. 추정한 필드만 표시한다

탄수화물만 비어 있고 지방이 있는 행(647건), 그 반대(105건)가 실제로 있다.
**채운 것만 `estimatedFields`에 넣는다** — 원본에 있던 값까지 추정으로 표시하면
표시가 무의미해진다.

## API

`FoodResponse`에 필드 하나가 는다. **추가일 뿐이라 iOS를 안 고쳐도 안 깨진다**(Swift
`Codable`은 모르는 키를 무시한다).

```kotlin
data class FoodResponse(
    // ...
    /** 추정으로 채운 필드. `["carbs","fat"]`. 비었으면 전부 원본 값이다. */
    val estimatedFields: List<String>,
)
```

문자열이 아니라 **배열로 내보낸다** — 앱이 `contains("carbs")`로 쓰게 하고, 서버의
저장 형식(쉼표 문자열)이 계약에 새지 않게 한다.

## ⚠️ 먼저 읽을 함정 넷

### 함정 1 — 컬럼을 늘리면 **적재된 DB가 조용히 옛날 값을 유지한다**

`FoodSeeder`는 데이터셋별로 `existsByDataset`을 보고 이미 있으면 건너뛴다. CSV 컬럼을 14→15로
늘려도 **이미 적재된 DISH·RAW·PROCESSED는 다시 안 들어온다.** `estimated_fields`는 컬럼만
붙고 전부 null이 되며, 13,405행도 안 들어온다. 겉으로는 배포가 성공한 것처럼 보인다.

**→ 재적재가 필수다. 다만 `delete from food;`는 과하다.**

```sql
delete from food where dataset = 'DISH';
delete from food where code like 'MANUAL-%';
```

**`RAW`·`PROCESSED`는 지우지 않는다.** 그쪽은 탄단지가 완비된 행만 들어와 있어서
`estimated_fields`가 null인 게 **맞는 값**이다(추정한 필드가 없다). 원재료 523행은 그대로 두고,
가공식품 306,293행은 라즈베리파이에서 다시 넣는 데 몇 분이 걸리므로 헛되이 재적재하지 않는다.

**수동 등록분은 따로 지워야 한다.** 데이터셋 검사를 안 타서 매 기동 다시 훑기는 하지만
`on conflict (code) do nothing`이라, 이미 들어 있는 86행은 **조용히 건너뛰어져
`estimated_fields`가 null로 남는다.** 코드가 그대로라 겉으로는 정상으로 보인다.

**지우기 전에 세 CSV를 모두 새 형식으로 다시 만들어 둔다** — 옛 14컬럼이면 파서가
`columns.size < COLUMN_COUNT`로 전부 버린다. `PROCESSED`를 지우지 않더라도, 나중에 누군가
지우고 다시 넣을 때를 위해 파일은 새 형식이어야 한다.

### 함정 2 — 되살린 13,405행이 **완전일치 매칭 순서를 바꾼다**

`FoodMatcher.match`는 `DISH` 완전일치를 가장 먼저 본다. 음식DB가 6,090 → 19,495행으로
3.2배가 되면서 **지금까지 원재료나 가공식품으로 가던 이름이 조리 음식에 먼저 걸린다.**
`findFirstByDatasetAndNormalizedName`은 정렬이 없어 어느 행이 걸릴지 DB 순서에 달렸다.

되살린 행은 탄·지가 추정이므로, **원본 값을 가진 행이 있으면 그쪽이 이겨야 한다.**

**→ 완전일치 쿼리에 정렬을 준다.** 추정이 없는 행이 먼저다.

**여기서 `@Query`로 그냥 바꾸면 안 된다.** 지금은 파생 쿼리라 `findFirst` 접두사가 `LIMIT 1`을
붙여 주는데, **`@Query`를 달면 그 접두사가 무시된다.** 같은 데이터셋에 같은 정규화 이름이
이미 여러 건 있어서(DISH 6,090행 중 **1,084종 3,452행**이 중복이다 — 상추겉절이 8건,
무말랭이무침 7건) 곧바로
`IncorrectResultSizeDataAccessException`이 난다. 끼니 확정 경로가 통째로 죽는다.

> `2026-07-31-meal-merge-by-type-design.md`가 `findByUserAndDateAndMealType(): Meal?`로
> 똑같이 밟았던 함정이다.

**→ `List` + `Pageable`로 받고 호출부가 `firstOrNull()` 한다.** 이름도 바꾼다 —
`findFirst`가 남아 있으면 다음 사람이 같은 착각을 한다.

```kotlin
@Query("""
    select f from Food f
    where f.dataset = :dataset and f.normalizedName = :normalized
    order by case when f.estimatedFields is null then 0 else 1 end, f.id asc
""")
fun findBestByDatasetAndNormalizedName(
    @Param("dataset") dataset: FoodDataset,
    @Param("normalized") normalized: String,
    pageable: Pageable,
): List<Food>
```

`FoodMatcher.match`의 세 줄이 `.firstOrNull()`을 붙이는 형태로 바뀐다.

같은 정렬을 부분일치(`searchByDatasetAndNormalizedName`)에도 준다. **이걸 안 하면 되살린
추정 행이 멀쩡한 원본 행을 밀어낸다** — 되살리기가 오히려 정확도를 떨어뜨린다.

### 함정 3 — 검색 결과가 3.2배가 되면서 **찾던 게 뒤로 밀린다**

`searchByText`는 `order by length(f.normalizedName) asc, f.id asc`다. 피자 4,227행이
들어오면 「피자」 검색의 상위 50건이 전부 되살린 피자로 찬다. 사용자가 찾던 것이 51번째가 된다.

**→ 검색 정렬에도 추정 여부를 앞에 둔다.** 이름 길이보다 먼저다 — 짧은 이름의 추정 행보다
긴 이름의 원본 행이 낫다.

### 함정 4 — 아트워터 필터가 **기준 표본과 되살릴 행을 동시에 정의한다**

비중을 낼 때 `|4탄 + 4단 + 9지 − 열량| > 열량×15%`인 행을 기준에서 뺀다(원본에도 자기모순인
행이 있다). **그 필터를 되살릴 행 판정에도 쓰면 안 된다** — 되살릴 행은 애초에 탄·지가 없어
아트워터를 계산할 수 없다. 두 집합의 정의를 한 함수로 합치면 `13,405`가 `13,459`가 되는 식으로
조용히 어긋난다(실제로 측정 중에 겪었다).

## 테스트

**고의 파손을 반드시 돌린다.** 아래 각 항목 옆이 「그걸 없앴을 때 빨개져야 하는」 자리다.

- **추정 없는 행이 완전일치에서 이긴다** — 같은 이름으로 원본 행과 추정 행을 넣고
  원본이 나오는지. *정렬을 지우면 빨개져야 한다*(함정 2)
- **같은 이름이 여러 건이어도 예외가 안 난다** — 정규화 이름이 같은 행 3건을 넣고
  `FoodMatcher.match`가 하나를 돌려주는지. *`Food?` 반환 `@Query`로 만들면 빨개져야 한다*.
  **이 테스트가 없으면 함정 2를 밟고도 통과한다** — 테스트 데이터에 중복 이름이 없으면
  단건 반환이 멀쩡히 동작하고, 실제 DB에서만 터진다
- **검색에서도 추정 없는 행이 먼저다** — 이름이 더 긴 원본 행이 짧은 추정 행보다 앞인지.
  *`estimatedFields` 정렬 항을 빼면 빨개져야 한다*(함정 3)
- **원본에 있던 값은 추정으로 표시하지 않는다** — 탄수화물만 비고 지방이 있는 행에서
  `estimatedFields == "carbs"`인지. *`"carbs,fat"`으로 뭉뚱그리면 빨개져야 한다*
- **모르는 필드명은 무시하되 행은 살린다** — `estimatedFields`에 `carbz`가 와도 행이 들어오는지
- **15컬럼이 아닌 옛 CSV는 버려진다** — 14컬럼 행이 `null`이 되는지(함정 1의 조용한 실패를 잡는다)
- **물리 하한** — 당류 ≤ 탄수화물, 포화지방 ≤ 총지방, 아트워터 검산.
  **수동 CSV 전 행에 이미 걸려 있다**(`FoodSeederTest`). 되살린 CSV에도 표본 검사로 건다
- **`FoodSeeder`가 21개 컬럼을 순서대로 넣는다** — 컬럼 수와 `?` 수와 세터 인덱스가 맞는지
