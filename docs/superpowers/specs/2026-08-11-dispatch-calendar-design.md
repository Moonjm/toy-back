# 부모님 근무 달력 (서버) 설계

작성일: 2026-08-11
짝 저장소: `woori-haru` (iOS — 업로드·검수 화면), `toy-repo` (웹 — 무인증 조회 달력)
이 문서는 **서버를 중심으로** 쓰되, 세 저장소가 맞물리는 지점을 함께 적는다.

## 배경

**아빠와 엄마가 각각 언제 일하고 언제 쉬는지**를 한 달력에서 보려는 것이다. 지금은 매달
사진을 눈으로 훑어 옮겨 적고 있다.

두 사람의 일정이 들어오는 경로가 완전히 다르다.

**아빠 — 배차표 사진.** 카카오톡 밴드로 매달 버스 배차표 사진이 올라온다. 엑셀 표를 찍은
것이고, 왼쪽에 `[차량번호, 성명]` 컬럼이 있고 오른쪽으로 그 달의 날짜 칸이 이어진다.
칸에 숫자(1/2/3…)가 있으면 근무이고 그 숫자가 배차 순번이다. **빈 칸이면 휴무다.**
사진은 두 종류로 온다 — 월초에 **그 달 전체 배차표**가 올라오고, 중간에 변경이 생기면
**바뀐 뒷부분만 잘린 사진**이 다시 올라온다. 잘린 사진에는 **성명 컬럼이 없다.**

**엄마 — 반복 패턴.** 사진이 없다. `하루 휴무 → 이틀 근무`가 3일 주기로 반복된다
(2026-08-08이 휴무). 이 주기는 **설정에 고정되어 등록 절차 없이 항상 계산된다** —
저장소에 두면 등록하기 전까지 달력에서 엄마가 통째로 비어 보이는데, 그게 「쉬는 날」인지
「등록을 안 한 것」인지 화면만으로는 구분되지 않는다.
근무 이틀에 순번 구분이 있긴 하지만 **지금은 넣지 않는다** — 나중에 채우거나, 아빠처럼
사진 인식으로 발전시킬 여지를 남긴다.

경로는 다르지만 **조회는 하나로 합쳐 나간다.** 웹 달력은 `role`에 따라 색만 다르게 칠하고,
그 데이터가 사진에서 왔는지 패턴에서 왔는지 알 필요가 없다.

**실명과 차량번호는 저장하지 않는다.** 조회 달력이 무인증으로 열려 있어서다. DB에도 API
응답에도 남기지 않고, `role`(`FATHER`/`MOTHER`)만 오간다.

## 실측 — 근거 데이터

설계 전에 실제 사진 두 장으로 OpenRouter를 호출해 측정했다. 아래 숫자가 이 설계의 근거다.
정답은 원본을 확대해 사람이 판독한 값이다.

| 모델 | 전처리 | 정확도 | 재현성 | 호출 비용 |
|---|---|---|---|---|
| `gemini-2.5-flash` | 없음 | **0%** (31일 전부 환각) | — | $0.003 |
| `gemini-2.5-flash` | 조각 확대 | 78~100% | ❌ 호출마다 다름 | $0.003 |
| `gemini-2.5-pro` | 조각 확대 | 67~100% | ❌ 흔들림 | ~$0.05 |
| `gemini-3.6-flash` | 없음 | ❌ 뒤로 갈수록 밀림 | — | $0.012 |
| **`gemini-3.6-flash`** | **조각 확대** | **100%** | **✅ 6회 전부 동일** | **$0.017** |

`gemini-3.6-flash` + 전처리 조합은 9일치·17일치 조각에서 **6회 연속 정답과 완전히 일치**했다.
저해상도 밴드 스크린샷에서도 대상 기사의 성명·차량번호·`2026-8`·`rowIndex=2`를 정확히 읽었다
(`2.5-flash`는 같은 사진에서 성명 한 글자를 틀리게 읽었다).

## ⚠️ 먼저 읽을 함정 다섯

### 함정 1 — **사진을 그대로 넣으면 전부 지어낸다**

가장 먼저 시도할 방법이고, **가장 확실하게 실패한다.**

`2.5-flash`에 원본 사진을 그대로 넣으면 31일을 **빈 칸 하나 없이 전부 숫자로** 채워
돌려준다. 대상 행은 실제로 절반 이상이 빈 칸인데도 그렇다. `3.6-flash`도 원본
그대로는 뒤로 갈수록 한 칸씩 밀리고, 다른 기사 행의 값(`21:휴 22:휴`)이 섞여 들어온다.

원인은 해상도다. 표가 가로로 길어 한 칸이 몇 픽셀밖에 안 되고, 그 크기에서는 **빈 칸과
숫자가 구분되지 않는다.** 모델은 구분이 안 되는 자리를 비워 두는 대신 메운다.

**→ 표 영역을 잘라 확대한 뒤에 넘긴다.** 이 전처리가 이 기능의 성패를 가른다.
같은 사진·같은 모델인데 전처리 유무로 0%와 100%가 갈렸다.

### 함정 2 — **모델을 `2.5-flash`로 두면 같은 사진이 매번 다르게 읽힌다**

이 저장소는 이미 `2.5-flash`를 vision 모델로 쓰고 있어(`OpenRouterProperties.visionModel`)
그대로 재사용하고 싶어진다. **음식 인식과 표 판독은 요구가 다르다.**

전처리를 똑같이 한 이미지에 `2.5-flash`를 5회 호출한 결과다(정답은 `1:1 2:_ 3:2 4:_ 5:1 6:_ 7:1 8:_ 9:1`):

```
r1  1:1 2:_ 3:2 4:_ 5:1 6:1 7:2 8:_ 9:1     7/9
r2  1:1 2:_ 3:2 4:_ 5:1 6:_ 7:1 8:_ 9:1     9/9
r3  (JSON 파싱 실패)
r4  1:1 2:1 3:2 4:_ 5:1 6:_ 7:1 8:_ 9:1     8/9
r5  1:1 2:1 3:2 4:1 5:1 6:1 7:1 8:1 9:1     5/9
```

`2.5-pro`도 같은 이미지 2회에 9/9와 6/9가 나왔다. **비싼 모델로 올린다고 해결되지 않는다.**

**→ `gemini-3.6-flash`를 쓴다.** 같은 조건에서 6회 연속 정답과 완전히 일치했다.
`visionModel`을 갈아끼우지 말고 **배차 전용 설정 키를 따로 둔다** — 식단 인식은 `2.5-flash`로
잘 돌고 있고, 배차 때문에 그쪽 비용을 5배로 올릴 이유가 없다.

재현성이 확보되면서 **다수결 호출도 필요 없어졌다.** 한 조각에 1회만 호출한다.

### 함정 3 — **잘린 사진에는 이름이 없다. 행 순서가 유일한 단서다**

변경분 사진은 오른쪽만 잘려 와서 **성명 컬럼이 통째로 없다.** 그 사진만 보고는 어느 줄이
대상 기사인지 알 방법이 없다.

세로는 잘리지 않는다 — 제목·요일 헤더·기사 13행이 모두 보인다. 그래서 **「위에서 3번째
데이터 행」이라는 위치**가 성립한다. 전체본을 넣을 때 이 위치를 기억해 두면 이후 잘린
사진은 그 위치로 읽을 수 있다.

**이 매칭은 조용히 어긋날 수 있다.** 배차표 인원이 바뀌어 행 순서가 밀리면 **엉뚱한 기사의
근무가 아빠 달력에 들어가고, 아무도 눈치채지 못한다.**

**→ 두 가지로 막는다.**
1. 인식할 때 **표의 전체 데이터 행 수**를 함께 받아, 저장된 행 수와 다르면 경고를 띄운다.
2. 응답에 `matchedBy`(`NAME` / `ROW_INDEX`)를 실어, 위치로 매칭한 경우 **검수 화면이 그 사실을
   눈에 띄게 알린다.** 사용자가 사진과 대조할 근거를 준다.

`DispatchRoster`가 없는 달에 잘린 사진만 올라오면 **거부한다.** 추측해서 저장하느니
"전체본을 먼저 올려 주세요"가 낫다.

**여기에 순환이 하나 숨어 있다.** 어느 달의 `DispatchRoster`를 조회할지 알려면 사진에서
연·월을 읽어야 하는데, 사진을 읽으려면 어느 행을 읽을지 — 즉 `rowIndex`를 — 알아야 한다.
현재 달로 대신하면 **8월 말에 9월 배차표를 미리 올릴 때 엉뚱한 달의 기준을 본다.**

**→ 연·월을 요청에서 받는다.** 앱은 어느 달 배차표인지 알고 있다. 사진에서 읽은 달과
요청한 달이 다르면 `YEAR_MONTH_MISMATCH` 경고를 달아 엉뚱한 달에 저장되는 것을 막는다.

성명 컬럼이 없는 것으로 판별되면 **첫 조각도 행 위치로 다시 읽는다.** 이름으로 물어
얻은 답은 어느 행을 읽었는지 알 수 없어 믿을 수 없다. 잘린 사진일 때만 드는 추가 호출
하나($0.017)다.

### 함정 4 — **집계 컬럼을 날짜로 세면 그 뒤가 전부 밀린다**

표에는 날짜 컬럼 사이사이에 `계`(주간 합계)·`2주 합계`·`합계`·`총근무`가 끼어 있다.
이걸 날짜로 세면 **그 지점 이후 모든 날짜가 한 칸씩 밀린다.** 실제로 프롬프트에 명시하기
전에는 `day 7 → "4"`, `day 8 → slot 5` 같은 값이 나왔다. 4와 5는 날짜 값이 아니라
주간 합계다.

**→ 프롬프트에 집계 컬럼을 명시적으로 제외시키고, 응답에 `visibleDays`(그 조각에서 보이는
날짜 헤더 목록)를 함께 받는다.** 합칠 때 **칸 하나씩** `visibleDays`에 들어 있는지 보고,
없는 날짜의 칸은 버린다(집계 컬럼을 날짜로 센 흔적이다). 명시한 뒤로는 `계` 컬럼을 정확히
건너뛰었다.

조각 단위로 통째 불신하지는 않는다 — 조각의 픽셀 범위와 날짜를 대응시키려면 어느 픽셀이
어느 날짜인지 알아야 하는데 그 정보가 없고, `visibleDays`의 연속성 검사는 조각 경계에서
정상적으로 끊기는 경우까지 오탐으로 잡는다. 칸 단위 필터로 충분하다.

### 함정 5 — **인식 결과를 바로 저장하면 틀린 값이 조용히 박힌다**

`3.6-flash`가 실측에서 100%를 냈다고 해서 **항상 100%인 것은 아니다.** 사진 품질은 매달
다르다 — 흔들리거나, 더 축소되거나, 세로가 잘릴 수 있다. 그때 나온 값이 검증 없이 저장되면
달력은 **틀렸다는 사실조차 알려주지 않는다.**

**→ 인식과 저장을 API 단위로 분리한다.** `POST /dispatch/recognitions`는 **아무것도 저장하지
않고** 결과만 돌려준다. 사용자가 앱에서 사진과 나란히 놓고 확인·수정한 뒤
`POST /dispatch/shifts`로 확정한 것만 저장된다.

## 데이터 모델

`apps/daily-record` 안에 `com.toy.backend.dispatch` 패키지를 새로 만든다.
`daily-record` DB를 그대로 쓴다.

```kotlin
enum class DispatchRole { FATHER, MOTHER }

@Entity
class DispatchShift(              // (role, workDate) 하나당 한 행
    val role: DispatchRole,       // UNIQUE(role, workDate)
    val workDate: LocalDate,
    var working: Boolean,         // 그날 일하는가 — 판정은 오직 이 값으로
    var slot: Int?,               // 배차 순번(1/2/3…). 근무여도 미정이면 null
    var note: String?,            // 원문 표기: 휴, 간담회, 예비군, *97, -
) : BaseEntity()

@Entity
class DispatchRoster(             // 아빠 전용 — 월별 배차표 행 위치
    val yearMonth: String,        // "2026-08"  UNIQUE
    var rowIndex: Int,            // 데이터 행 0-based
    var rowCount: Int,            // 그 달 표의 전체 데이터 행 수 (함정 3의 경고 근거)
) : BaseEntity()

// 엄마 반복 규칙은 엔티티가 아니라 설정이다 (dispatch.mother-pattern)
data class MotherPatternProperties(
    val cycleDays: Int = 3,
    val workingOffsets: String = "1,2",   // 주기 안에서 일하는 날의 오프셋
    val anchorDate: LocalDate = LocalDate.of(2026, 8, 8),  // 오프셋 0 = 휴무인 날
)
```

### `working`을 `slot`과 따로 두는 이유

「`slot`이 있으면 근무」로 판정하고 싶어진다. 아빠 데이터만 보면 실제로 그렇게 맞는다.
**엄마에서 깨진다** — 엄마는 근무일이지만 순번이 아직 없어 `slot`이 `null`이고, 그러면
**근무일이 전부 휴무로 읽힌다.**

나중에 순번을 채워 넣기로 한 결정이 이 함정을 만든다. 「값이 없음」에 두 가지 뜻(휴무 /
아직 모름)을 겹쳐 실으면, 순번을 채우는 날 판정 로직을 **읽는 쪽마다 전부** 고쳐야 한다.

**→ `working`이 판정의 유일한 근거다.** `slot`은 표시용 부가 정보이고, `note`도 마찬가지다.

```
working=false            → 휴무 (note가 있으면 '휴'·'간담회'·'예비군' 원문을 함께 보여준다)
working=true, slot=null  → 근무, 순번 미정   ← 지금의 엄마
working=true, slot=1     → 1번 근무
```

`휴`·`간담회`·`예비군`은 근무가 아니라는 것이 합의된 규칙이므로 `working=false`에
`note`만 채운다. 원문은 화면에 그대로 보여주되 **판정에 끼어들지 않는다.**

### 실명을 어디에 두는가

`DispatchRoster`에 `driverName`·`vehicleNo`를 두지 않는다. 그런데 **전체본에서 행을
찾으려면 인식 시점에는 이름이 필요하다.**

**→ 이름은 서버 환경변수에만 둔다.**

```yaml
dispatch:
  father-name: ${DISPATCH_FATHER_NAME:}
```

프롬프트를 만들 때만 쓰이고 어디에도 저장되지 않는다. DB·API 응답·웹 화면 어디에도
실명이 남지 않는다. 이름이 비어 있으면 인식 요청을 거부한다 — 이름 없이 부른 프롬프트는
아무 행이나 읽어 온다.

### 엄마 패턴을 어떻게 펼치는가

`DispatchShift`에 미리 만들어 넣지 않는다. **조회할 때 계산한다.**

```
offset = floor((날짜 - anchorDate) / 1일) mod cycleDays     // 음수 보정 필요
working = offset in workingOffsets
```

`anchorDate = 2026-08-08`, `cycleDays = 3`, `workingOffsets = [1, 2]`이면 8/8·8/11·8/14…가
휴무이고 나머지가 근무다. 8월은 **8/2, 8/5, 8/8, 8/11, 8/14, 8/17, 8/20, 8/23, 8/26, 8/29**가
휴무로 나온다.

미리 만들어 넣으면 **패턴을 고칠 때 이미 생성된 행이 낡은 채로 남는다.** 어디까지 만들어
뒀는지도 관리해야 하고, 미래 날짜를 조회하면 빈 달이 나온다. 계산은 나눗셈 하나다.

**예외는 `DispatchShift`에 저장한다.** `role=MOTHER` 행은 **패턴과 다른 날만** 들어간다.
조회할 때 패턴으로 채운 뒤 저장된 행으로 덮어쓴다. 나중에 순번을 채우는 것도 같은
자리다 — 그날 `DispatchShift` 행을 만들어 `slot`을 넣으면 된다.

## API

| 엔드포인트 | 인증 | 하는 일 |
|---|---|---|
| `POST /dispatch/recognitions?yearMonth=` | 필요 | 배차표 사진 인식(아빠). **저장하지 않고** 결과만 반환 |
| `POST /dispatch/shifts` | 필요 | 검수 확정분 upsert. **보낸 날짜만** 갱신 |
| `GET /dispatch/shifts?yearMonth=` | **불필요** | 웹 달력 조회. **아빠·엄마를 합쳐** 반환. 무인증이라 기간이 아닌 **연월 하나**를 받아 범위를 한 달로 못 박는다 |

`GET`만 `SecurityConfig`에서 `permitAll`로 연다. 무인증 조회는 **읽기 전용이고 이 한
엔드포인트뿐**이며, 응답에 실명·차량번호가 없다(`role`만 나간다).

**조회 응답** — 아빠는 저장된 행에서, 엄마는 패턴을 펼친 뒤 예외로 덮어써서 만든다.
읽는 쪽은 둘을 구분할 필요가 없다.

```jsonc
{
  "days": [
    { "date": "2026-08-01", "role": "FATHER", "working": true,  "slot": 1,    "note": null },
    { "date": "2026-08-01", "role": "MOTHER", "working": true,  "slot": null, "note": null },
    { "date": "2026-08-02", "role": "MOTHER", "working": false, "slot": null, "note": null }
  ]
}
```

아빠는 **확정 저장된 날짜만** 나간다. 아직 인식·검수하지 않은 날은 응답에 없고, 달력은
그 자리를 비운다. 「쉬는 날」과 「아직 모르는 날」을 색으로 구분하기 위해서다. 엄마는
패턴으로 계산하므로 조회 범위 전체가 항상 채워진다.

**인식 응답**

```jsonc
{
  "yearMonth": "2026-08",
  "hasNameColumn": true,
  "matchedBy": "NAME",           // NAME | ROW_INDEX
  "rowIndex": 2,
  "rowCount": 13,
  "warnings": ["ROW_COUNT_CHANGED"],  // ROW_COUNT_CHANGED | YEAR_MONTH_MISMATCH. 비어 있을 수 있다
  "days": [
    { "day": 1, "working": true,  "slot": 1,    "note": null,  "conflict": false },
    { "day": 2, "working": false, "slot": null, "note": null,  "conflict": false },  // 휴무
    { "day": 3, "working": false, "slot": null, "note": "*97", "conflict": true }
  ]
}
```

**실명과 차량번호는 응답에도 싣지 않는다.** 모델이 읽더라도 버린다 — 검수 화면이 그
값을 쓸 일이 없고, 한 번 응답에 실으면 앱 로그·캐시에 남는다. 이름이 맞게 찾아졌는지는
`matchedBy`로 알 수 있다.

`matchedBy`는 **`hasNameColumn`이 결정한다.** 사진에서 대상 이름을 찾았으면 `NAME`이고,
그 경우 인식된 `rowIndex`·`rowCount`로 `DispatchRoster`를 갱신한다. 이름 컬럼이 없으면
저장된 `rowIndex`를 써서 읽고 `ROW_INDEX`가 된다.

`conflict`는 겹친 구간에서만 `true`가 될 수 있다. 두 조각의 답이 갈렸을 때 **어느 쪽도
고르지 않고 둘 중 왼쪽 조각의 값을 실어 보내되 `conflict: true`를 단다.** 판단은 검수하는
사람이 한다.

**사진에 보이지 않는 날짜는 `days`에 넣지 않는다.** 0이나 휴무로 채우면 「쉬는 날」과
「모르는 날」이 구분되지 않고, 잘린 사진을 올릴 때마다 안 보이는 구간이 휴무로 덮인다.

`POST /dispatch/shifts`도 같은 이유로 **받은 날짜만 upsert**한다. 월 전체를 지우고 다시
넣으면 이전에 확정한 날짜가 사라진다.

## 전처리

`java.awt.image.BufferedImage` + `javax.imageio`로 서버에서 처리한다. 외부 라이브러리를
쓰지 않는다.

1. **여백 트리밍** — 가장자리부터 단색 행/열을 걷어낸다. 확대 캡처의 검은 여백과 밴드
   스크린샷의 흰 배경·UI 영역이 여기서 빠진다.
2. **가로 2등분, 경계 10% 겹침** — 실측에서 17일치 조각까지 100%가 나왔으므로 2등분이면
   충분하다. 겹치는 이유는 **경계에 걸친 날짜가 양쪽에서 잘려 유실되는 것**을 막기 위해서다.
3. **업스케일** — 각 조각을 긴 변 1600px로 키운다.
4. **PNG 인코딩 후 base64.**

겹친 구간에서 두 조각의 답이 다르면 그 날짜에 `CONFLICT` 표시를 달아 검수 화면이
강조한다. 겹침이 만들어 주는 **공짜 교차검증**이다.

## LLM 호출

기존 `OpenRouterClient`의 `visionBody` 패턴을 따르되 **배차 전용 설정을 별도 키로 둔다.**

```yaml
dispatch:
  vision-model: ${DISPATCH_VISION_MODEL:google/gemini-3.6-flash}
  vision-max-tokens: ${DISPATCH_VISION_MAX_TOKENS:30000}
```

**`max_tokens`를 크게 잡아야 한다.** `3.6-flash`는 reasoning 토큰을 1,300~3,000 쓰는데
이 값이 `max_tokens`에 함께 잡힌다. 기존 식단용 4,000으로 두면 `content`가 **빈 채로**
온다(`2.5-pro`에서 실제로 재현됐다). `OpenRouterProperties` 주석에 적힌 402 함정과 같은
계열이므로, 값을 지우지 말고 넉넉히 준다.

**재시도를 1회 넣는다.** 실측에서 5회 중 1회 JSON 파싱에 실패했다. 기존
`OpenRouterClient`는 「실패 반복이 곧 비용 폭주 경로」라 재시도를 하지 않지만, 여기는
**사용자가 사진을 다시 올려야 하는 대면 흐름**이고 조각당 $0.017이다. 1회로 제한한다.

응답은 strict `json_schema`로 고정한다. `visibleDays`(함정 4)와 `rowCount`(함정 3)를
스키마에 포함시킨다.

## 검수 화면 (iOS, `woori-haru`)

- 위쪽에 업로드한 사진(핀치 줌), 아래에 인식된 날짜 목록.
- 각 행은 `날짜 · 요일 · 값`. 값을 탭하면 `휴무 / 1 / 2 / 3 / 직접입력`.
- **`matchedBy == ROW_INDEX`면 상단에 배너**를 띄운다 — "성명 컬럼이 없어 3번째 줄로
  맞췄습니다. 사진과 대조해 주세요."
- `warnings`에 `ROW_COUNT_CHANGED`가 있으면 경고를 함께 띄운다.
- `CONFLICT` 날짜는 색으로 구분한다.
- 사진에 없던 날짜는 「미인식」으로 두고 **저장에서 제외**한다.

## 조회 화면 (웹, `toy-repo/apps/daily-record`)

`App.tsx`에 `RequireAuth` **없는** 라우트를 추가한다.

```tsx
<Route path="/shift" element={<ShiftCalendarPage />} />
```

기존 `DayCell`은 기록·짝꿍·과식·생일 데이터에 강하게 결합돼 있어 재사용하지 않는다.
건드리면 기존 달력이 회귀한다. **배차 전용 셀을 얇게 새로 만들되**, 격자 CSS
(`cal-grid`/`cal-cell`), 주말·공휴일 색 규칙, `getMonthCells` 로직은 그대로 따른다.

한 날짜 칸에 **아빠·엄마 두 개의 뱃지**가 들어간다.

- 뱃지 색이 사람을 구분한다. `role`에 색을 하나씩 배정하고 순서를 고정한다(아빠 위, 엄마 아래).
- **근무일만 뱃지를 그린다.** 휴무일은 그 사람 뱃지를 아예 그리지 않는다 — 두 사람 것이
  같은 칸에 있어서, 휴무를 회색 뱃지로 그리면 칸이 색 덩어리로 뭉개진다.
- 뱃지 안에 `slot` 숫자를 넣는다. `slot`이 `null`이면 **숫자 없이 색만** 칠한다(지금의 엄마).
- `note`가 있으면 원문을 작게 덧붙인다.

색만으로 누가 누구인지 알 수 없으므로 **달력 위에 범례를 둔다.** 색맹 대비로 색에만
기대지 않도록, 범례와 뱃지에 같은 라벨(`아빠`/`엄마`)을 함께 쓴다.

## 테스트

- **전처리** — 여백 트리밍이 검은 여백과 흰 여백을 모두 걷어내는가. 2등분 경계가 겹치는가.
- **병합** — 잘린 사진이 **보이는 날짜만** 덮어쓰는가. 안 보이는 날짜가 휴무로 덮이지 않는가.
- **행 매칭** — `DispatchRoster`가 없는 달에 `hasNameColumn == false` 사진이 오면 거부하는가.
  `rowCount`가 달라지면 `ROW_COUNT_CHANGED` 경고가 붙는가. 요청한 달과 사진의 달이 다르면
  `YEAR_MONTH_MISMATCH`가 붙는가.
- **시계 비의존** — 인식 로직과 그 테스트가 「오늘」에 의존하지 않는가. 연·월은 요청에서 온다.
- **판정** — `note`가 `휴`/`간담회`/`예비군`인 날이 근무로 새지 않는가. **`slot`이 `null`인
  근무일(엄마)이 휴무로 읽히지 않는가** — `working`만 본다.
- **패턴 전개** — `anchorDate` 이전 날짜(음수 오프셋)가 올바로 계산되는가. 8월이
  `8/2·8/5·8/8·8/11·8/14·8/17·8/20·8/23·8/26·8/29` 휴무로 나오는가.
- **패턴 예외** — `role=MOTHER` `DispatchShift` 행이 패턴 계산 결과를 덮어쓰는가.
- **조회 병합** — 아빠는 저장된 날짜만, 엄마는 범위 전체가 나오는가.
- **개인정보** — 인식·조회 응답 어디에도 실명과 차량번호가 실리지 않는가.
- **응답 파싱** — `visibleDays`가 조각 범위와 어긋나면 그 조각을 버리는가.
- LLM 호출 자체는 기존 `OpenRouterClientTest`처럼 **요청 본문 구성**만 검증한다.

## 하지 않는 것

- **배차표 전체 기사 13명 저장** — 사진에서 읽는 대상은 아빠 한 행이다. 인원이 늘면
  `DispatchRoster`를 `role`별로 두면 된다.
- **엄마 순번(1번/2번) 채우기** — 구분이 있긴 하지만 지금은 `slot`을 비워 둔다. `working`과
  분리해 뒀으므로 나중에 `slot`만 넣으면 되고, 사진 인식 경로로 발전시켜도 자리는 같다.
- **엄마 패턴을 미리 행으로 만들어 두기** — 조회할 때 계산한다. 미리 만들면 패턴을 고칠 때
  낡은 행이 남는다.
- **다수결 호출** — `3.6-flash`가 재현성을 확보해 근거가 사라졌다(함정 2).
- **표 영역 자동 검출** — 여백 트리밍과 2등분까지만 한다. 표 경계를 찾는 것은 별개 문제이고,
  실측상 여기까지로 100%가 나왔다.
- **자동 저장** — 검수를 반드시 거친다(함정 5).
- **웹에서의 업로드·수정** — 업로드는 인증된 iOS 앱에서만 한다. 웹은 읽기 전용이다.

## 운영 메모

권장 캡처 방식은 **시간표만 확대해서, 첫 장은 성명 컬럼이 보이게 왼쪽부터**다. 그러면
한 장으로 행 식별과 값 판독이 동시에 된다. 세로는 기사 행이 모두 들어가야 한다 —
행이 잘리면 순번 매칭이 깨진다(함정 3).

밴드 글을 통째로 찍은 스크린샷은 **행 위치 확인에는 쓸 수 있지만 값 판독에는 못 쓴다.**
표가 화면의 20%밖에 안 돼 확대해도 한계가 있다.
