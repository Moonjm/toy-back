# 관리비 고지서 사진 인식·기록·추이(`/maintenance/*`) 신설을 기록한다

## 변경

- **`POST /maintenance/recognitions` 신설.** 고지서 사진을 Gemini Vision(`gemini-3.7-flash`)에
  넣어 항목·사용량·부과액을 읽는다. **저장하지 않고 결과만 돌려준다** — 검수용이다. 사진 자체도
  저장하지 않는다(`common/file`의 `FileEntity`에 소유자가 없는 미해결 이슈를 건드리지 않으려고,
  AGENTS.md).
- **`POST/GET/PUT/DELETE /maintenance/bills`, `/maintenance/bills/{yearMonth}` 신설.** 검수를
  마친 결과를 연월(`year_month_value`, unique) 단위로 확정 저장·조회·수정·삭제한다. 리소스
  주소가 DB id가 아니라 연월이라 `POST` 응답의 `Location`도 `{id}` 자리에 연월이 들어간다.
- **`GET /maintenance/trends?months=` 신설.** 항목·사용량의 월별 추이를 낸다. 기본 13개월(전년
  동월이 범위에 들어온다), 상한 60개월. **없는 항목은 0으로 채우지 않고 `null`로 둔다** — 특히
  난방은 여름 몇 달이 항목 자체가 없다. 0으로 채우면 「난방을 안 썼다」와 「그 달에 난방 항목이
  없었다」가 구분되지 않는다.
- **`MaintenanceBill`·`MaintenanceBillItem` 엔티티.** 부과액·항목 합계·사용량 5필드
  (`electricityKwh`·`waterM3`·`hotWaterM3`·`heatingGcal`·`foodKg`, 전부 nullable)를 담는다.
  사용량 5필드는 엔티티·DTO(`MaintenanceDtos.kt`)·저장 서비스·추이 서비스 네 곳 모두에 있어야
  앱까지 값이 간다 — 이 저장소는 같은 사고로 「사진으로 기록한 모든 끼니가 나트륨 0」을 이미
  겪었다.
- **배차(`dispatch`) 비전 모델 기본값을 `gemini-3.6-flash`에서 `gemini-3.7-flash`로 맞춘다.**
  운영은 이미 3.7로 돌고 있는데 코드 기본값이 3.6으로 남아 있어, 환경변수를 지우면 조용히 3.6으로
  돌아가는 상태였다. 관리비 비전 클라이언트를 새로 만들면서 같은 실수를 반복하지 않으려고 먼저
  고쳤다.

## 과거 넉 달(2025-08~11)을 SQL로 이관한다 — 인식을 태우지 않는다

이 넉 달은 종이 영수증이 아니라 관리비 앱(아파트아이) 화면 캡처로만 남아 있다. 그 형식에는
연도·동·호·면적·납기일·사용량이 없다. 되풀이될 형식이 아닌데 인식 프롬프트가 그것까지
감당하게 만들면, 종이 영수증과 앱 캡처 어느 쪽으로도 확실하지 않은 프롬프트가 된다. 그래서
`scripts/maintenance-import/2025-08_2025-11.sql`에 사람이 판독한 값을 그대로 INSERT하는
쪽을 택했다.

- 금액 84개(항목 83개 + 부과액 4개)는 캡처를 확대해 사람이 읽었다. 네 달 모두 항목 합계가
  화면의 납부금액과 일치하는 것을 이미 확인했다(275,570 / 287,690 / 217,740 / 236,190).
- 사용량 20개(4개월 × 5필드)는 2025-12 영수증에 딸린 「호실별 사용량 추이표」에서 옮겼다. 그
  표의 25/12 행이 2025-12 영수증 본문의 사용량과 정확히 일치해 표 해석 자체가 검증됐다.
  2025-08~10의 난방은 표 칸이 비어 있어(여름) `NULL`이다 — `0`이 아니다.
- 항목명은 종이 영수증 기준으로 통일했다(`세대전기료→전기`, `세대급탕비→온수`,
  `세대수도료→수도`, `세대난방비→난방`). 통일하지 않으면 전기료 추이가 2025-11과 2025-12
  사이에서 한 번 끊긴다.
- 스크립트 끝의 `SELECT`는 항목 합계와 부과액이 맞는지 사람이 눈으로 보는 용도다. 그 위에
  같은 조건을 다시 검사하는 `DO` 블록을 얹어, 하나라도 어긋나면 예외를 던져 트랜잭션 전체를
  롤백한다. `psql -f`(또는 `docker exec -i ... < file.sql`)로 파일을 통째로 돌리면 사람이
  중간에 개입할 수 없어 `SELECT` 결과만으로는 잘못된 값의 커밋을 막지 못하기 때문이다.

## 검증 방식

- 84개 금액과 20개 사용량 모두 브리프 원문과 한 자리씩 자동 diff로 대조해 일치를 확인했다
  (항목 83줄, bills 4줄 모두 diff 결과 없음).
- 이관 SQL을 도커의 실제 운영 PostgreSQL(`pg-postgis`, `daily-record` DB, 두 테이블 모두
  실행 전 0행)에 직접 돌렸다. 검증 `SELECT`가 네 달 모두 `ok`, `DO` 블록 통과, `COMMIT` 성공.
- `psql`로 `전기`/`세대전기료` 이름 두 가지를 모두 조회해 `전기` 4줄만 나오고
  `세대전기료`는 0줄임을 확인했다(이름 통일 확인).
- `psql`로 `heating_gcal`을 조회해 2025-08~10은 `NULL`, 2025-11만 `0.0400`임을 확인했다
  (여름 난방 NULL 확인).
- `/maintenance/*`는 인증이 걸려 있어 로컬에 자격 증명이 없는 이번 확인에서는 curl로 추이
  API를 직접 호출하지 못했다. 위 두 psql 조회로 API가 보게 될 원본 데이터를 대신 확인했다.

## 이번에 하지 않은 것

- **추이 API 실호출.** 인증 자격 증명이 로컬에 없어 위 psql 조회로 대신했다. 앱이 실제로
  배포된 뒤 확인이 남는다.
- **사진 저장.** `FileEntity` 소유자 이슈가 해결되기 전까지는 계속 미룬다.
